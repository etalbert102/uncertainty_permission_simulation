# Prespecified Worked-Trace Rule

Status: fixed selection semantics; executable Slice 3 trace and blinded/oracle renderings available; independent QA pending

Specification: `data/scenarios/worked_trace_spec_v1.yaml`

## Rule

The main article uses the paired trace with fixed specification ID `RB-WORKED-TRACE-001`. It is not selected from pilot or confirmatory outputs. No alternative trace may replace it because it is more dramatic, cleaner, or more supportive of a hypothesis.

The pair combines the immutable R-OCI-Early source fixture and application mapping with a separately study-owned stylized trace overlay. The deterministic compiler produces a process capability profile, selects the active U policy and independent evaluation specification, resolves every runtime slot, and emits one compiled configuration per arm. The source fixture supplies documented topology and transition meaning; the overlay supplies the synthetic case, amounts, access state, resources, and timing values that the historical record does not establish. The pair holds the synthetic case, aggregate evidence, latent period values, notice/access condition, later evidence availability, process capability graph, resources, clocks, evaluation rules, and all keyed draws fixed. It varies only the declared active policy profile:

- baseline arm: early-OCI-structured impute-and-progress path; and
- repair arm: agency-assisted information-first hold and retrieval path.

The trace must run through the declared restoration horizon. Its explanatory job is to show how a supported or unsupported action, recovery exposure, later correction, and residual consequence are separately recorded. It is not an estimate of a typical Robodebt case.

## Eligibility Gate

The trace is renderable only if:

1. its stored input records match the versioned specification exactly;
2. each arm has a valid compiled configuration with zero unresolved slots and one binding receipt per runtime parameter;
3. no overlay overwrites a documented value or treats an unsupported source value as executable history;
4. both arms use identical exogenous case and draw hashes;
5. the early process capability profile and U1/U3 policy implementations pass their unit tests;
6. all events pass conservation, ordering, and reference validation;
7. the baseline includes the declared nonresponse, imputation, progression, later evidence, reassessment, and partial-restoration path;
8. the repair arm includes the declared evidence-acquisition, hold, supported disposition, and avoided-exposure path;
9. all F0–F5/helper rows follow the frozen property contracts; and
10. no event or output is manually edited for presentation.

If the fixed trace fails an implementation or semantic gate, fix the implementation or version this specification before confirmatory output inspection. Do not substitute another case. If the underlying scenario is logically invalid, record that failure and use a schematic trace rather than silently selecting a favorable run.

## Rendering Rule

The manuscript and practitioner report render the stored trace and assessments. They may omit nonmaterial event detail for space but may not recompute facts from prose. The display must include:

- evidence type and provenance;
- representation/imputation transition;
- configured gate and actual review state;
- exact progression, information, constraint, and restoration actions;
- deadline and queue state where applicable;
- recovery exposure;
- later correction and any residual consequence;
- diagnostic and intervention owners; and
- explicit claim limits.

## Change Control

The following are semantic changes requiring a new specification version and pre-confirmatory review:

- case attributes or period values;
- arm policies;
- evidence or notice timing;
- deadline or restoration horizon;
- action classification;
- evaluation support, materiality, or restoration rules; and
- the eligibility or rendering rule.

Display-only changes that cannot alter status, completeness, diagnosis, ownership, tradeoff, or claim boundary may retain the version with a logged rationale.
